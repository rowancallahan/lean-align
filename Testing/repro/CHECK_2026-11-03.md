## Where the instructions were wrong, missing or ambiguous
1. **Disk and truncated downloads** (not mentioned): the setup needs about 40 GB free, and a short asset is silent with a hand `gh api` download (added to the README).
2. **R5 "rules A-E"**: the script prints `HARD A..D`, `info C`, `info F`, `info H`; rule E has no line of its own (it is the `info H` "minibwa has both mates at the origin" lines). README wording fixed. The audit docstring still lists E and G, the output uses H.
3. **`real_vs_minibwa.py` writes `SET.examples.tsv` into the current directory**; `real_rescore.sh` works around it with `mv`, which fails if the script is run from a directory other than the repo root. Better: an output directory argument.
4. **`mapping.sh`/`real_rescore.sh`/`fuzz_audit.sh` assume `Testing/data/prebuilt` and `Testing/data/downloads/hg38.upper.fa`**; with the release fetched by hand (no `fetch_release.sh`) the symlinks have to be made first (`shim.idx`, `mb.l2b`, `mb.mbw`, reads, the genome); `fuzz_audit.sh` regenerates a 3 GB `hg38.1l.fa` inside OUT even if one exists elsewhere unless `OUT/hg38.1l.fa` is already there (symlink works).
5. **`proofs.sh` writes `/tmp/ci_repro.log`**, a fixed path (collides with parallel runs; fine otherwise).
6. **Timings**: `proofs.sh` took 2 min 29 s here (README 1 min 39 s), `fuzz_audit.sh` 3 min 52 s (4 min 25 s), `fuzz_ci.sh` 10.7 s (`fuzz_ci.sh` header says "about a minute").
7. **minibwa is not bit-reproducible across read order/names** (item in the R5 row): compare minibwa columns only when the exact FASTQ (names, order) is the one the notes used; ours reproduces exactly.
8. **samtools**: the README build recipe (`autoreconf -i`) is for a git checkout; the release tarballs of htslib/samtools 1.24 (github.com/samtools/*/releases/download/1.24/) need only `./configure --without-curses ...; make` and avoid autoconf. Not tested here (build refused).
