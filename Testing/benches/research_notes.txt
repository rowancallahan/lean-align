Q1. Where minibwa spends its time, and why it is fast
------------------------------------------------------
callgrind (20k reads, instructions; 88.7 k instructions/read):
  seeding (SMEM finding, FM-index rank/extend)    49%   (bwt_rank1a/2a, smem_batch)
  SA lookup (positions of seed hits)               6%
  base alignment (ksw2 extd2 SSE + glue)          35%   (ksw_extd2_sse alone 24%)
  chaining (lchain)                              2.4%
  output (SAM formatting)                        3.5%
  index load (10-mer interval cache)             10% of the whole run, once
gprof (100k reads, time): rank1a 27%, rank2a 16%, sa_batch 16%, ksw_extd2 9%,
  extend 4%, mimalloc page init 11% (load), everything else < 3%.
=> Time is ~2/3 FM-index random memory access (seeding + SA), ~10-25%
   alignment, the rest small.

Design choices that make it fast (read in bwt.c, seed.c, align.c, dev.md):
- FM-index SMEMs with a precomputed table of the SA intervals of all 10-mers
  (`mb_bwt_cache`): the first 10 backward steps of every seed are one lookup.
- Batching across reads with software prefetch (`mb_bwt_smem_batch`: a queue
  of reads, each step issues `__builtin_prefetch` for the next occ block and
  moves to another read).  dev.md credits this with 2.5x on SMEM finding.
  SA lookups are batched the same way (`mb_bwt_sa_batch`).
- Skipping DP when it cannot matter (`mb_align_pair`): for equal-length
  query/target it scores the ungapped diagonal; with <= 3 mismatches (or a
  score no gapped alignment can beat) it returns without SIMD DP.  The
  mismatch count also narrows the DP band.
- SIMD ksw2 (SSE, 16 cells per instruction) for the rest.
- Down-weighting highly repetitive regions (`max seed occurrences` 250).
  This is a heuristic.  We cannot copy it: the spec says ties make a read
  unmapped, so repeats must be decided exactly.
- k-mer cache, 2-bit packed reference (l2bit), mimalloc, kalloc arenas.


Q2. Fastest exact strategy for our problem
------------------------------------------
Key fact (the basis of Proto2): with match 0, mismatch -4, gap 6+2L and
T = -12, every window with penalty <= 12 is one of
   (a) length n, Hamming distance h <= 3, penalty 4h
       (any gapped alignment of equal lengths needs >= 2 gaps = >= 16);
   (b) length n+L or n-L, L in {1,2,3}, exactly one gap run of L letters,
       penalty 6+2L, plus at most one mismatch when L = 1 (8+4 = 12).
Also every window with penalty < 12 is ungapped or a single gap with no
mismatch.  So no DP is needed.  For an anchor diagonal d (where an exact
seed puts the read's start), the candidate windows are
   (d, n); (s, n+L) for s in {d, d-L}; (s, n-L) for s in {d, d+L}
and each is decided by forward/backward mismatch scans on diagonals d-3..d+3:
   deletion window (s, n+L): a0(s) + b0(s+L) >= n, or for the 1-mismatch case
       a1(s)+b0(s+L) >= n or a0(s)+b1(s+L) >= n;
   insertion window (s, n-L): the same with + L on the left side and s-L,
where a0/a1 = length of the read prefix with 0/<=1 mismatches on a diagonal,
b0/b1 the same for suffixes.  That is 7 forward + 7 backward scans per anchor.
This is the WFA recurrence specialised to a score cap of 12 (the scans are
WFA's "extend" steps), with every window end at once.

Exact-match shortcut: any window of penalty 0 equals the read, so it contains
all 4 seeds at fixed offsets.  The hits of the RAREST seed (smallest index
bucket) therefore list every exact copy: 1 copy => mapped at penalty 0
(nothing can beat 0), >= 2 copies => unmapped (tie at the best possible
score), stop after 2.  On sim this decides 60.8% of reads (57.3% unique,
3.5% repeated) with no other seed and no scan; measured 2.4x overall.
Generalisation (tiers): an alignment with penalty p has at most E(p) events
(E = 0 for p < 4, 1 for p < 8, 2 for p < 12, 3 at 12) and each event spoils
at most one of the 4 disjoint seeds.  So if two distinct windows tie at p,
or one window has penalty p, only windows with <= E(p) events can compete,
and they all show up in the E(p)+1 rarest seeds.  This bounds the work in
repeats exactly.

k-mer CSR vs FM-index for 25 bp pigeonhole seeds:
- Lookup: CSR = 1 offset read + 1 contiguous range (1-2 cache misses).
  FM backward search = 25 dependent LF steps, ~2 misses each (minibwa needs
  the 10-mer cache, batching and prefetch to make that cheap).  For fixed
  seeds the hash/CSR index is cheaper per lookup, and it is far easier to
  prove: completeness of a table built by one pass over the genome, versus
  BWT/SA correctness.
- Repeats: FM gives the number of exact copies of a whole read in ~100 LF
  steps without listing them.  The CSR only lists them, but the rarest-seed
  rule plus stopping at 2 copies makes the exact case cheap anyway.  For
  non-exact reads in repeats both must enumerate candidates.
- Memory: chr21 12-mer CSR = 38 M entries; at 4 B each (ByteArray) 152 MB,
  as Array UInt32 (boxed, 8 B) 304 MB, plus 64 MB of offsets.  minibwa chr21
  index: 93 MB FM + 12 MB 2-bit genome, 0.2 GB RSS.  See Q4 for the whole
  genome.
- Measured problem with 12-mer keys: 327 bucket hits per non-exact read
  (82 per seed, because reads land in repeats more than the mean bucket of
  2.3), each verified by a random genome access.  Storing the next 13
  letters (26 bits) with each index entry removes those misses
  (34.7 k -> 39.8 k reads/s before the scan rewrite).  On the whole genome a
  12-mer key is hopeless (~77x more hits per bucket); key on the full 25-mer
  (Q4).

Non-ACGT letters: Proto.lean codes N as A, so ~8.6 M N positions land in the
poly-A 12-mer bucket.  Proto2 leaves words containing a non-ACGT letter out of
the index and ORs a non-ACGT mask into the packed mismatch mask.  That is
exact for ACGT reads.  A proved mapper also needs a fallback for reads with
non-ACGT letters (rare: 1 in 100 k here, ~0.1% in real Illumina data), for
example a small index of the genome's non-ACGT positions, or scanning those
seeds as unusable while the remaining seeds still satisfy the pigeonhole.


Q3. Kernel: WFA vs banded DP vs bit-parallel
--------------------------------------------
- Banded DP as in Proto.lean: 7 window starts x 100 rows x 7 cells = 4,900
  cells per anchor, ~14 anchors per non-exact read => ~69 k cells per read.
  Measured ~1 k reads/s => roughly 15-30 ns/cell in Lean with boxed Nat
  arrays and 3 fresh arrays per row.  A tight unboxed loop would be ~2-5
  ns/cell, still ~50-300 us per read; SIMD (ksw2: ~0.1 ns/cell) is not
  available in Lean without @[extern].
- WFA at a cap of 12: the reachable penalties are 0,4,8,10,12, at most 7
  diagonals, and each extend is one LCP.  That is ~100 word ops per window
  start.  The closed form above is that computation with every window end
  done at once: 14 scans per anchor, each 1-4 64-bit XOR/popcount steps on
  a 2-bit packed genome.  Measured in Lean: 100-letter Hamming with packed
  words + USize/uget = 21 ns (hot cache), against 662 ns for a
  `for i in [0:n]`/`get!`/Nat byte loop.
  If the scoring or T must stay generic, a capped, ends-free WFA is the
  generic form of the same thing.  It needs a new proof: the repo's proved
  WFA is global for one window pair, so it would cost 49 runs per anchor.
- Bit-parallel Myers / BitPAl: unit-cost or linear-gap edit distance, not
  affine with open 6.  It would have to be used as a lower-bound filter and
  is not exact for this spec by itself.  Not worth it here.
- Cells/read: closed form = 14 scans x ~4 words x ~14 anchors ~= 800 word ops
  per non-exact read, about 0 for the 61% exact reads.  Proto2 spends ~1/3 of
  its time here after the rewrite; the rest is index lookups (cache misses).


Q4. Index layout at chr21 and whole-genome scale
------------------------------------------------
- chr21, 12-mer CSR, all positions: fine.  Offsets 64 MB, positions 152 MB
  packed.  Lookups are 1-2 misses.  Add the 13 extension letters (another
  152 MB) or use longer keys.
- Whole genome (3.1 G letters, 2.94 G ACGT): all-positions CSR of 12-mers =
  11.8 GB packed, 23.5 GB as Array UInt32, with ~175 hits per bucket.  Not
  viable.
- Recommended: exact SAMPLED index keyed on longer words.  Index the k-mers
  at genome positions p = 0 mod s, with k + s - 1 <= 25 (e.g. s = 4, k = 22,
  or s = 8, k = 18).  Look up the s k-mers at offsets 0..s-1 inside each
  25 bp seed.  If the seed occurs at g0, one of g0..g0+s-1 is sampled, so the
  lookup stays complete.  That is exact, unlike a heuristic minimizer
  sketch.  Hash buckets (2^28 x 4 B = 1 GB) plus entries of (pos 4 B,
  32-bit fingerprint of the rest of the key, so false bucket hits never
  touch the genome).  s = 4: 735 M entries x 8 B = 5.9 GB; s = 8: 2.9 GB.
  Packed genome 0.78 GB plus non-ACGT mask (0.78 GB as a bitmap, or a short
  list of N runs).  Total ~4-8 GB, the same range as minibwa
  (~2.25 B/letter on chr21 => ~7 GB).  Cost is 4s lookups per read before
  the rarest-seed early exit; batch them across reads (rank 8).
- Minimizers give a slightly better density per lookup but need a lemma
  about window minima and tie-breaking.  Fixed sampling (p mod s) has the
  same density guarantee and an arithmetic proof.  Prefer sampling.
- Positions must be 4-byte packed in a ByteArray, not Array UInt32 (8 B,
  boxed) or Array UInt64 (each element a heap object).  The genome must be
  2-bit packed (Proto2 `pack`), not one byte per letter, and not List Char.
- Build or load: Proto2 builds the chr21 index in 7-26 s per run (prototype
  code).  minibwa loads a prebuilt index in 0.6 s.  Serialize the index
  (IO.FS.readBinFile -> ByteArray is a memcpy) and prove the checker or
  builder once.


Q5. Lean code patterns (bench/Micro.lean, `lake exe micro`, IR in .lake/build/ir)
------------------------------------------------------------------------------
Measured (ns per call, 10 M calls):
  random gather, Array UInt32 (boxed, 8 B/entry)          96-107  (cache-miss bound)
  random gather, ByteArray 4-byte little-endian            82-91   (half the memory)
  Hamming 100 B, for/get!/Nat                    hot 662   cold 830
  Hamming 100 B, USize + uget, tail recursion    hot 211   cold 274
  Hamming 100 letters, 2-bit packed, Nat get!    hot 102   cold 176
  Hamming 100 letters, 2-bit packed, USize+uget  hot  21   cold  35
  returning (Nat x Nat) (allocates a ctor)            10
  returning a packed UInt64                           3.7
  harness loop overhead                               4.5
Findings from the generated C:
- Nat indices compile to lean_nat_add/mul/shiftr with overflow checks and a
  lean_dec after each.  `get!` adds a bounds check and a panic path.  Use
  USize indices with `uget`/`a[i]'h` and discharge bounds with small lemmas
  (Proto2 `idx_le`: (i + ofNat k).toNat <= i.toNat + k, 3 lines).  clang then
  merges the 8 byte loads of a little-endian word into wide loads (checked
  with objdump).
- UInt64.log2 is a LOOP in lean.h (`while (a >= 2) a /= 2`).  Using it for
  ctz/clz made the packed scans no faster than bytes.  Use popcount-based
  ctz/msb (Proto2 `ctz`, `msb`; SWAR popcount, since leanc has no -mpopcnt).
- `while` loops and `for` loops with several `mut` variables carry their
  state as boxed objects (repeatM_erased / forIn loops take lean_object*).
  A mutable UInt64 in such a loop is heap-allocated on every iteration.
  Rewriting the scans as tail-recursive functions with UInt64 arguments and a
  Nat fuel parameter took Proto2 from 40 k to 58-60 k reads/s (stress: 19 k
  -> 36.5 k).
- Tuples, Option and small structures returned from hot functions allocate
  unless inlined.  Pack them into UInt64 or mark the function @[inline].
  Array UInt64 elements are heap boxes; ByteArray and FloatArray are the only
  unboxed arrays in core.
- Proto.lean's DP allocates 3 arrays per row (Array.replicate) and its loop
  state tuples (74 lean_alloc_ctor sites in Proto.c).  Arrays updated in
  place are fine when the reference is unique (`set!` on a `let mut` array
  compiles to an in-place update after the first copy).
- Input: String.splitOn plus UTF-8 validation of the 46 MB FASTA is 19% of
  Proto's instructions at load.  Read with IO.FS.readBinFile and parse bytes.
- Pure code is moved across IO.monoNanosNow by the compiler (lets are sunk to
  their use).  Benchmarks must make the work depend on the clock or run it
  through an IO action (see Proto2's par mode).
- Threads: Task.spawn over 4 chunks reaches 55-58 k reads/s.  One task alone
  is only 33 k against 58-60 k for the same loop on the main thread.  Marking
  the hot functions' parameters @& (borrowed) did not change it.  My
  untested guess: objects reachable from a task become multi-threaded, so
  their reference-count updates turn atomic.  Not resolved.  Next step:
  callgrind the 1-task run, look for lean_inc/lean_dec on idx/g/pk in the
  hot path, or run one process per core.
- No prefetch intrinsic and no SIMD without @[extern], which is banned in
  codecs/pool/spec.  Latency hiding has to come from issuing independent
  loads together (batching lookups across reads, so out-of-order execution
  overlaps the misses).


Q6. How much of minibwa's speed is SIMD/prefetch vs algorithm (measured)
------------------------------------------------------------------------
Three local builds of the same source, same reads; all give byte-identical
SAM (same md5).  Mapping time for 100k reads, 10 runs each, min / median:
  default (-msse4.2 -mpopcnt, SSE4.1 ksw2, prefetch)  1.61-1.76 / 1.85 s
  SSE2 only (no SSE4.1 ksw2 path, software popcount)  1.57 / 1.75 s
  prefetch removed (-D'__builtin_prefetch(...)=')     1.70 / 1.75 s
  (objdump: the SSE2 build has 0 popcnt and 0 pblendvb/pmaxsb; the no-prefetch
  build has 0 prefetch instructions)
=> On chr21 single-thread, SSE4.1 vs SSE2, hardware popcount, and software
   prefetch are each below the +-10% run-to-run noise.  The 93 MB chr21
   FM-index is small enough that prefetch matters little.  dev.md reports
   2.5x on SMEM from batching+prefetch, presumably on the whole genome
   (3 GB index, every step a DRAM miss).  Expect prefetch to matter there.
- The SIMD DP itself cannot be switched off: ksw2 has no scalar path, and
  SSE2 is the x86-64 baseline.  gprof puts ksw_extd2_sse + ksw_extz2_sse at
  ~10% of mapping time, with 0.78 DP calls per read.  A 16-lane kernel
  replaced by scalar code costing ~8-16x more would add 70-150% to the run.
  Estimate: SIMD is worth ~1.7-2.5x on this workload, all of it in the DP.
- The rest is algorithmic: the ungapped shortcut avoids DP for most reads;
  the 10-mer interval cache removes the first 10 of ~25+ LF steps per seed;
  chaining is cheap.  Seeding is the dominant cost (Q1).

Q7. What holds Lean-compiled code back vs C here, and what proved code can avoid
-------------------------------------------------------------------------------
Measured context: the old banded DP costs ~15-50 ns/cell in Lean (bench/Proto
and the other session's ~50 ns); scalar C is ~1 ns, SIMD ~0.1 ns.  Item by
item (avoidable = can be avoided in code that is still proved, without
@[extern]/unsafe/implemented_by):
  boxed objects       Nat/Int and Array elements are lean_object*.  Avoidable:
                      UInt64/UInt32/USize locals and arguments are unboxed C
                      values; ByteArray (and FloatArray) are the only unboxed
                      arrays.  Array UInt64 elements are heap boxes; use a
                      ByteArray with 8-byte decode (clang merges the loads).
  reference counting  lean_inc/lean_dec on every object passed or projected.
                      Mostly avoidable: @& (borrowed) parameters for the
                      genome/index, scalars instead of objects in hot loops.
                      Atomic RC on objects shared with tasks may explain the
                      unresolved 1-task slowdown (Q5).
  bounds checks       get!/set!/[i]! check and keep a panic path.  Avoidable:
                      uget/a[i]'h with a proof, often by one range check per
                      window (`if h : i + 8 <= a.size`) plus a small lemma.
  Nat arithmetic      lean_nat_add/mul with overflow checks and a lean_dec per
                      op; Int is worse.  Avoidable: USize/UInt64 with proofs
                      relating .toNat; keep Nat in specs and lemmas only.
  closures in loops   for/while in do-notation compile to specialised loop
                      functions.  State with several `mut` vars or a while
                      loop's state is passed boxed (repeatM_erased takes
                      lean_object*), so a UInt64 there is heap-allocated each
                      iteration.  Avoidable: explicit tail recursion with
                      scalar arguments and a Nat fuel or termination proof.
                      40 k -> 58-60 k reads/s in Proto2.
  copy-on-write       Array.set! copies when the array is shared (RC > 1).
                      Avoidable: keep DP rows/accumulators uniquely referenced
                      (no second live binding, no capture in a closure), or
                      allocate once per read and reuse.  Proto.lean allocates
                      3 arrays per DP row: avoidable.
  allocation/iter     tuples, Option, structures and boxed UInt64 allocate.
                      Avoidable: pack into UInt64, @[inline] small helpers
                      (pair return 10 ns vs packed 3.7 ns).
  library traps       UInt64.log2 is a loop in lean.h; String.splitOn plus UTF-8
                      validation on FASTA input.  Avoidable: popcount-based
                      ctz/msb, readBinFile + byte parsing.
  no SIMD/prefetch    Not avoidable without @[extern].  64-bit SWAR (2-bit
                      letters, 32 per word) recovers much of it for exact and
                      Hamming work: 21 ns per 100-letter compare.
Net: with these rules the hot path is plain scalar C (checked in
.lake/build/ir/*.c and objdump).  Only SIMD and prefetch stay out of reach.
For this problem the closed form removes the DP, so the missing SIMD costs
little.

Q8. Near-exact reads (0-2 differences, as in the user's trimmed reads)
---------------------------------------------------------------------
minibwa: always runs full SMEM seeding, SA lookup and chaining.  Only the
DP is skipped: equal-length query/target with <= 3 mismatches (or no gapped
alignment can beat it) is scored ungapped; extensions with <= 1 mismatch
too.  The mismatch count narrows the DP band otherwise.  So near-exact reads
still pay the dominant seeding cost.
Ours (exact, all provable):
- penalty 0: the rarest-seed shortcut (1 bucket, verify, stop at 2 copies)
  decides the read; no other seed, no scan.
- penalty 4 (1 mismatch): any competitor with penalty <= 4 has <= 1 event and
  no gap (a gap costs >= 8), so it is an equal-length window with Hamming
  <= 1 on a diagonal of one of the 2 rarest seeds.  Hamming checks only,
  4 XOR/popcount words each.
- penalty 8 (2 mismatches or one 1-bp gap): 3 rarest seeds.  Equal-length
  windows by Hamming, plus the 1-bp gap cases (a0 + b0 >= n checks) on
  d +- 1 only.
- penalty 12: all 4 seeds, full closed form.
This is the plan the other session describes ("<= 1 mismatch needs only
Hamming").  The general rule is in Q9.

Q9. Seed strategies asked about: two-pass 2x50 / 4x25, order + early stop, learned order
-------------------------------------------------------------------------------------
Early stop (best penalty P so far => only floor(P/4)+1 seeds):
  Correct, exact.  Every event costs >= 4 (mismatch 4, gap >= 8), so a window
  with penalty <= P has <= floor(P/4) events.  Each event spoils at most one
  of the 4 disjoint seeds, so any floor(P/4)+1 seeds contain an unspoiled
  one.  Competitors at penalty = P must be found too (a tie makes the read
  unmapped), and they are covered by the same bound.  Procedure: read the 4
  bucket sizes first (offsets only), take seeds in increasing size, keep the
  best P, and stop once the number of seeds examined exceeds floor(P/4).
  P = 0 -> 1 seed, 4 -> 2, 8 -> 3, 12 -> 4.  Gapped windows need checking
  only when P >= 8.
  Proof: medium.  "Seeds spoiled <= events <= floor(P/4)" (the existing
  MapperWalk lemma generalised from 1 untouched seed to 4 - E untouched),
  plus "the windows found so far are all hits with penalty <= P".
Seed order (rarest first, by bucket size, or a learned order):
  Any order is exact: the proof quantifies over the set of seeds examined,
  never their order, so an order picked by a learned table, by bucket
  sizes, or at random needs no extra proof.  Exact bucket sizes cost one
  offset read per seed and are the best per-read signal.  A learned
  per-seed-pair order can only help when bucket sizes tie or when offset
  reads themselves are the cost.  Expect little over rarest-first.
  Proof: trivial (take the seed set as a parameter).
Two-pass 2x50 then 4x25:
  2 x 50: one 50-mer is exact when there is <= 1 event (P <= 7: 0 or 1
  mismatch).  Its advantage is selectivity in repeats (a 50-mer has fewer
  copies than a 25-mer).  Its cost: a separate 50-mer index costs a second
  full position table (chr21: +152 MB; whole genome: +11.8 GB unsampled,
  +3-6 GB sampled).  You get the same selectivity with no new memory by
  looking up the 25-mer half of each 50-mer in the existing index and
  verifying the other 25 letters from the stored extension/fingerprint or
  the packed genome.  Pass 1 = rarest 25-mer, then extend to 50 before the
  candidate is accepted.  With the early-stop rule above, pass 1 is just the
  P <= 7 tier.  I would not build a second index.
  Proof: easy-medium (the pigeonhole for 2 halves is the same lemma with 2
  seeds; the extension check is a filter whose soundness is equality of
  letters).


Q10. Aeneas: hot path in safe Rust, translated to Lean and proved
-----------------------------------------------------------------
(Written offline from memory.  Everything about Aeneas's feature set is
TO VERIFY ONLINE [checked 2026-10-04, see Q12].)
What Aeneas is: Charon extracts rustc MIR, and Aeneas translates SAFE Rust
into a pure functional model in Lean 4 (also F*, Coq/Rocq, HOL4).  Mutable
borrows become "backward functions".  Fallible operations (indexing, integer
overflow, division) return Result, so each proof also shows no panic.  It
has been used on production cryptographic code (SymCrypt), which suggests
the loop and slice support is real.  TO VERIFY ONLINE [checked 2026-10-04, see Q12].
Supported subset (as I remember it; TO VERIFY ONLINE [checked 2026-10-04, see Q12]):
- yes: structs/enums, generics, traits (incl. trait-bound generics), u8..u64/
  usize with checked arithmetic, arrays, slices, Vec (through a model
  library), shared and mutable borrows incl. returning mutable borrows,
  loops (translated to recursive functions; loop invariants are proved in
  Lean), early return/break.
- partial: iterators and closures (simple `for i in 0..n` ok; general
  Iterator adapters and closures capturing &mut are limited), nested
  borrows inside data structures.
- no: unsafe (so no get_unchecked, no std::arch SIMD intrinsics, no raw
  pointers), interior mutability (Cell/RefCell), threads/Send/Sync/rayon,
  IO, allocation failure, panics as values.
Split if adopted:
- proved (Rust -> Lean model, then a Lean theorem that model = our Lean
  mapper or = mapSpec): mapRead per read (seed lookup, rarest-seed
  shortcut, closed form, unique best), index lookup, packed-genome scans,
  index builder or index checker.
- trusted Rust CLI: FASTA/FASTQ parsing, mmap/loading the serialized index,
  thread pool (rayon/std::thread over read chunks), SAM output.  The
  trusted surface grows: rustc + Charon + Aeneas translation + the CLI glue,
  where today it is the Lean compiler + Main.lean.
Expected speed-up over the Lean-compiled hot path (estimates, TO MEASURE):
- Proto2's hot path is already scalar C after the Q5/Q7 rules (unboxed
  UInt64/USize, uget, tail recursion).  What remains in Lean that Rust
  removes: RC traffic on the genome/index objects, Array UInt32 boxing (or
  ByteArray byte assembly), small allocations (result Arrays in
  fwdP/closedForm, tuples), and the unexplained Task slowdown (rayon would
  sidestep it).
- What stays: about half of Proto2's time is cache misses (index lookups,
  genome fetches), the same in any language.  Bounds checks remain in
  verified safe Rust unless LLVM elides them; SIMD needs unsafe intrinsics,
  so it is unverifiable.  Autovectorization of the 4-word XOR/popcount scan
  is small change.
- Estimate: 1.3-2x per thread end to end on chr21 (up to 3x on the compute-
  bound stress set), plus better thread scaling (minibwa gets ~2.7x on 4
  threads; Lean tasks currently give ~1x net).
Effort (estimate): 1-2 weeks to write the Rust hot path in the Aeneas
subset and get it through Charon/Aeneas; 3-6 weeks of proofs (loop
invariants on the generated model, no-overflow and no-out-of-bounds
obligations, then equality with the Lean mapper, reusing the Lean proofs of
items 1-2 above).  Cheaper route first: apply the Q7 rules, fix the
Task slowdown in Lean, and only move to Rust if a measured gap remains.
Note on the figures in the request ("~190k reads/s/thread vs minibwa ~34k"):
confirmed in ratio on this machine with the tuned prototype on
speed/proto-tune: ~5x minibwa (see "Cross-check" at the end).  My Proto2 is
a different, slower prototype.  With the hot path already ~5x minibwa,
Rust/Aeneas would buy a smaller share of the total; the case for it rests
on thread scaling and on the whole-genome index, not on per-read compute.

RANKED LIST OF CHANGES
======================
(speedup = measured on chr21/100k reads unless marked "est."; the proof is what
remains to do; "exact" = why the answer equals mapSpec)

1. Closed-form scoring instead of DP (Proto2 `closedForm`).
   Speedup: Proto 1.1 k -> 23.5 k reads/s with the shortcut off (~20x),
   0 disagreements on 120 k reads.
   Proof: medium-hard.  A characterisation lemma over AlignmentSpec
   alignments: with (0,-4,-6,-2) and T = -12, a window scores >= T iff case
   (a) or (b) of Q2, with that score.  Plus the window-candidate lemma
   (s in {d, d +- L}) and the scan lemmas (a0/a1/b0/b1 = first mismatch
   positions).  It can be stated for any ValidScoring by bounding the number
   of events from gapOpen/mismatch/T, but the default-scoring version is
   much smaller.
   Exact: it is a theorem about the scoring, not a heuristic.

2. Exact-match shortcut on the rarest seed, stop at 2 copies.
   Speedup: 2.4x on top of 1 (23.5 k -> 58 k reads/s); decides 61% of reads.
   Proof: easy-medium.  Penalty 0 <-> window = read (match score 0, every
   other column < 0).  Every exact copy contains every seed, so the rarest
   seed's hits are complete.  0 is the maximum score, so the unique-best
   rule settles the read (1 copy mapped, >= 2 unmapped).
   Exact: pigeonhole with zero errors.

3. Event-based error bound (prerequisite for 1, 2, 9).
   The proved mapper uses errBound = 12/min(4,2) = 6: 7 seeds of 14 bp and
   13 x 13 windows per hit.  The real bound is 3 events (each gap run costs
   >= 8), giving 4 seeds of 25 bp and a shift of <= 3.  This is what
   Proto/Proto2 assume; the speed/bounds branch is doing it.
   Speedup: est. 5-20x fewer candidates and DP calls in the proved mapper,
   and 25 bp seeds make lookups selective.
   Proof: medium (in progress on speed/bounds).

4. Unboxed data and loops: 2-bit packed genome in a ByteArray, USize/uget
   with bound lemmas, tail recursion with UInt64 arguments instead of
   while/for with mut state, no UInt64.log2, packed UInt64 returns.
   Speedup: Hamming 662 -> 21 ns (micro, 30x); Proto2 end to end 40 k ->
   58-60 k (the loop rewrite), stress 19 k -> 36.5 k.  Genome memory /4.
   Proof: medium.  One packing lemma (letters32 of the packed genome = the
   codes of 32 letters) plus mask/popcount/ctz lemmas.  bv_decide may
   discharge the bit tricks.  The non-ACGT mask needs one lemma.
   Exact: same values, different representation.

5. Index entries carry the seed's remaining letters (or a fingerprint).
   Speedup: 34.7 k -> 39.8 k reads/s (+15%; removes ~300 random genome
   reads per non-exact read).  Essential at whole-genome scale.
   Proof: easy.  ext[t] is a function of the genome at pos[t]; equality of
   codes <-> equality of ACGT letters; LookupComplete unchanged.

6. Whole-genome index: sampled k-mers (p mod s = 0, k + s - 1 <= 25),
   4-byte packed positions plus fingerprints in ByteArrays, serialized to
   disk.
   Speedup: needed to run at all (12-mer CSR would be 12-24 GB with
   ~175 hits per bucket); est. 4-8 GB total.
   Proof: medium.  New completeness lemma: a seed occurring at g0 has a
   sampled k-mer at offset (s - g0 mod s) mod s.
   Exact: completeness, not a sketch.

7. Threads with Task.spawn over read chunks (mapReadsPar on
   speed/dedup-parallel).
   Speedup: measured 1.75x from 1 to 4 tasks, but 1 task runs at 0.55x the
   main-thread loop, so the net gain over sequential is ~0 today.  Fix the
   single-task slowdown first (see Q5); minibwa gets ~2.7x at 4 threads
   (33 k -> 88 k in the task statement; here 2.86 s -> 0.72 s wall).
   Proof: trivial (= reads.map f).

8. Batch index lookups across reads (compute all bucket offsets for 8-16
   reads, then all ranges, then verify), so cache misses overlap.
   Speedup: est. 1.3-2x on the miss-bound part (minibwa: 2.5x on seeding
   with real prefetch; we only get out-of-order overlap).
   Proof: trivial (reordering pure maps); costs code complexity.

9. Seed order + early stop for non-exact reads (Q9): rarest seed first by
   bucket size; with best penalty P so far, stop after floor(P/4)+1 seeds;
   gapped checks only when P >= 8 (Q8).  50-mer selectivity, if wanted, via
   25-mer lookup + extension check, not a second index.
   Speedup: est. 10-30% on chr21, more for well-trimmed reads (most have
   P <= 4) and in whole-genome repeats.
   Proof: medium (seeds spoiled <= events <= floor(P/4); seed order needs
   no proof).

10. Correct non-ACGT handling: leave N-words out of the index, mask non-ACGT
    genome letters as mismatches, fallback for reads with non-ACGT letters.
    Speedup: avoids an 8.6 M-entry poly-A bucket on chr21 (Proto.lean codes
    N as A).  Required for exactness on real data anyway.
    Proof: small.

Proof difficulty in one line (easiest first): 7, 8 trivial; 5, 10 easy/small;
2 easy-medium; 3, 4, 6, 9 medium; 1 medium-hard.  All ten are exact, and
none needs @[extern], unsafe or implemented_by.

Optional later: Aeneas/Rust hot path (Q10), est. 1.3-2x per thread plus
working threads.  Proof hard (weeks), larger trusted base.  Do it only if a
measured gap remains after items 1-10.

Not recommended: FM-index/suffix array (large proof, 25+ dependent misses per
seed; its one advantage, counting repeats, is covered by 2 and 9);
bit-parallel Myers/BitPAl (not affine, not exact); SIMD or prefetch (needs
@[extern], banned in codecs/pool/spec); minibwa's repeat down-weighting
(heuristic, changes answers).
