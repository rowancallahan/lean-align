# n31 box O4 (2026-11-02): read-pair dedup, Int bignums on hg38, heuristic for M2

Branch `speed/n31-dedup-heur` on 5c309c3. Box: 4 cores, 15.7 GB RAM (Firecracker VM). hg38 release `bench-release`.
minibwa c07de5c, default build and `-march=native`. 4 threads, `taskset -c 0-3`, median of 3, one run at a time.

**Box noise:** system time of the same run varies 2–37 s (page faults while loading the 5.3 GB index); user time
±10% run to run. Index load (empty FASTQ): ours 1.9–32 s (pooled median 4.9 s), minibwa 10–27 s.
Wall − load is therefore rough; callgrind Ir is the reliable A/B.

## 3. The hg38 malloc/free and `__gmpz_init_set` (PAUSE table): one cause
Lean keeps an `Int` unboxed only up to 2^31 (`LEAN_MAX_SMALL_INT`); whole-genome positions reach 3.1·10^9, so every
`Int` window start (`addKF … ((e/16 : Nat) - n) …`, `dst n D sh`) was a GMP allocation (`lean_int_big_sub`,
`lean_big_size_t_to_int`, `Int.toNat`). glibc malloc/free on the profile were all `__gmp_default_allocate/free`.
chr21 (< 2^31) never showed it.

callgrind, shim, 2000 pairs, Ir per pair (empty-FASTQ run subtracted: 13.8M):
| set | base | b3131b2 | change | GMP + malloc share |
|---|---|---|---|---|
| NovaSeq | 843k | 756k | −10.3% | 5% → 0.02% |
| sim mason | 2.57M | 2.06M | −19.8% | 7% → ~0 |
CPU on the full sets did not move beyond the ±10% noise (table 4); the removed instructions were cheap next to the
cache misses of the bucket scans (`scanAWK`, 13–15% of Ir). Left on the profile: `diagsI`'s `List.mergeSort`
(10.5% of NovaSeq Ir; 248 sorts of ~716k Ir each, large diagonal lists) — §4 of EXPERIMENTS_NEXT.

- The heuristic adds 0.8–1.6% kept pairs on hg38; on the sims every added pair but 3–4 is at truth.
- Its CPU cost on hg38 is inside the ±10% noise for all settings, including XH=1 (on chr21 XH=1 was +62–92% on the
  real sets): the bench's per-pair cost is dominated by seed lookups on hg38, so the extra T2/T3 work is small next to it.
- best vs XH=1: 40–90 fewer pairs per set. cmax 24 / 40 keep the same pairs as cmax 16 on hg38 (±1) — the cmax
  trade-off of chr21 does not show here.
- In the shim (I/O included) the same CPU differences apply on top of the shim's ~2× multithreading overhead; extra
  SAM lines for ~2000 more mapped pairs per 200k are negligible. Not turned on in alignPairs (Rowan decides M2).
