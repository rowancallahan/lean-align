## New holes, ranked (check these against the next spec)

### N1 (HIGH): `alignPairs_correct` / `alignPairs_end_to_end` are false for some `InsertSettings` (unsatisfiable, so unprovable)
The theorems quantify over ALL `insertSettings`, but `junkScore` (floor on a reported pair) and `requiredMapBound` (a pair at or above it must be reported) are independent
`Int` fields. If `junkScore > requiredMapBound`, a pair whose best proper score s lies in `[requiredMapBound, junkScore)` has NO correct answer: `found = none` needs
`bestPossibleScore < requiredMapBound <= s`, which is false because the bound must be >= s; `found = some r` needs `r.score >= junkScore > s`, impossible because no proper pair scores above s.
Proved in the evidence file (`no_correct_answer`): genome = 100 x A, mates AAAA / TTTT, `range = (10,1000)`, `junkScore := 1`: the perfect pair (score 0) exists and NO `PairAnswer` is `Correct`.
So no implementation can satisfy `alignPairs_correct` for these settings; the Proofs/ side (`Answer.lean` is "not yet updated") cannot prove it as stated. (Settings with `junkScore <= requiredMapBound`, e.g. the defaults -50 / -16, are fine.)
Fix (smallest): a hypothesis `(h : insertSettings.junkScore ≤ insertSettings.requiredMapBound)` on both theorems, or a field `junkLeBound : junkScore ≤ requiredMapBound` in `InsertSettings` (the structure literal in Shim.lean then needs `by decide`).
Also useful: `requiredMapBound ≤ 0`-style sanity is not needed (positive values only make `found = none` easy).

### N2 (MEDIUM): a reported pair need not be near the best (the floor is absolute, `bestPossibleScore` is free)
`.unknown` with `found = some r` needs only `r.score >= -50` and `bestPossibleScore >= every proper pair`. So the laziest correct aligner reports ANY proper pair scoring >= -50 (for example the
second copy of a paralog at -44) as `unknown` with `bestPossibleScore := 0`, while the real best pair (score 0) is elsewhere: the SAM puts a "properly paired" record at the wrong copy (MAPQ 0, `XB:i:0` is the only hint).
Round 1 #1 for real reads shrinks to this. Fix: `.unknown` with `found = some r` also needs `answer.bestPossibleScore ≤ r.mate1.score + r.mate2.score + insertSettings.reportSlack` (new field, e.g. 16),
or require reporting a best-in-hand pair within slack of the bound.

### N3 (MEDIUM-LOW): the floor is on the pair sum and absolute
- Short reads: two mates of 4 letters as all-insertion at empty windows (-28) still satisfy `Correct` (evidence `lazy_correct_short`: report, bound 0, unknown); any pair of mates with total length <= 19 letters can be garbage (empty windows are legal placements).
  Relevant only if reads can be this short (no trimming now; with trimming back, short survivors are possible).
- One mate may be terrible while the other is perfect (-50 on one mate = 12 mismatches).
- Long reads: `requiredMapBound` -16 means nothing is REQUIRED to map when the best pair is below -16 (a 1 kb read with 1 % error is -40); `junkScore` -50 forbids reporting such pairs at all (13 mismatches).
  So every read longer than a few hundred bp at normal error rates is allowed to come back unmapped, and may not be reported even when the aligner finds the right place. Scale both by length (per base or fraction) before long reads are in scope.
Fix: floor per mate or scaled by length; forbid empty windows (`start < stop`) for non-empty reads.

### N4 (HIGH for data integrity): `readChunk` silently truncates or mispairs
Removed checks, new behaviour (Fastq.lean): `| _, _ => break` stops at the shorter file with NO error (one FASTQ shorter than the other, or a truncated last record, loses all remaining reads of the longer file and the program exits 0 with a shorter SAM);
mate-name comparison removed (R1/R2 out of step, one file filtered, shuffled files: arbitrary reads are aligned as "pairs"; the two output lines then even have different QNAMEs); the
sequence-length = quality-length check removed (QUAL of a different length than SEQ is printed: invalid SAM, silently). `@` and `+` are still not validated (`header.extract 1 header.size` drops any first byte).
Fix: restore the three checks as errors (they cost nothing); make `| some _, none | none, some _` an error.

### N5 (MEDIUM): zero-length reads give invalid SAM
Without trimming, an empty sequence line gives `some []` (theorem: aligned, empty window, empty CIGAR). `samSequence` no longer prints `*`, `cigarText #[] = ""`. Evidence (`#eval samLines` in this note's run):
`r1\t67\tchr1\t11\t0\t\t=\t11\t0\t\t\tAS:i:0\t...` has EMPTY CIGAR, SEQ and QUAL fields (SAM requires `*`), and the pair is flagged properly paired at an empty window (score 0).
Fix: restore `*` for empty SEQ/QUAL and empty CIGAR (`cigarText`), or treat empty reads as `none` again (`chunkPairs`).

### N6 (MEDIUM): trimming is gone from the shim but `PairResult.trimmedAway` stays in the spec
Stand-in: nothing is trimmed. Reads with adapter or low-quality tails align as mismatches (e.g. a 40 bp adapter tail = -160 -> below the floor -> allowed to be unmapped). Short-insert libraries (insert < read length) have read-through
mates that violate `dovetailSlack = 0` and are unmapped even with good bodies. `trimmedAway` can never be produced by this shim, so the theorem's `trimmedAway` arm is dead code. Round-1 #9 (trimmer outside the theorem) still applies when the trimmer returns.

### N7: round-1 holes that the new spec did NOT touch (still open)

#5 `N` matches `N` with 0; #6 case: lowercase never matches/complements, soft-masked FASTA accepted silently, `GenomeIsDNA` unchecked; #7 `AlignmentKernelCorrect` satisfied by `.unaligned 1` (proved) or huge `slack`;
#8 only proper pairs compete; #10 FASTA name = whole header line; #11 `.chromosomes` sidecar not tied to the index; #12 `range.1 > range.2` makes nothing proper;
#13 `IsProper` edge cases (RF excluded, reverse-inside-forward excluded, TLEN = fragment only for slack 0); #14 plumbing panics (`toNat!`, `fromUTF8!`), empty/tabbed QNAME, MAPQ stand-in, `XT` tier is printed but carries no claim.
See `SPEC_AUDIT_2026-11-02.md` for counterexamples and fixes.
