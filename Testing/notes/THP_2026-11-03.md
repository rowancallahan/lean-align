# Transparent huge pages for the index (SEARCH_IDEAS #3a): wall-time experiment, 2026-11-03

Box: cloud VM, 4 cores, 15 GB, THP `enabled = madvise`, glibc 2.39, no `perf` (no dTLB counters).
Binary: festive 9b81fb5 (new-format shim.idx, 5.34 GB). No code change: huge pages via
`GLIBC_TUNABLES=glibc.malloc.hugetlb=1` (glibc then `madvise(MADV_HUGEPAGE)`s its mmapped chunks; the index buffer is
one). Confirmed active: `AnonHugePages` rose to 3.2 GB during a run (0 without the tunable).

Protocol: NovaSeq 200k, `taskset -c 0-3`, index pre-read into the page cache before each pair of runs, an empty-FASTQ
run (index load only) then the full run; 10 runs per setting, settings interleaved (off, on, off, on per round).

| setting | empty run (load), median (min-max) | full run, median (min-max), sd |
|---|---|---|
| off | 4.58 s (2.40-10.87) | 8.52 s (8.02-10.55), 0.86 |
| hugetlb=1 | 2.81 s (1.76-4.92) | 8.45 s (7.51-10.69), 1.01 |

- Full runs: no difference beyond noise (-0.07 s on a 1 s sd). The load-only runs are faster with huge pages in this
  sample, but they are very noisy on this box (2.4-10.9 s off) and the full runs (which include the load) do not show it.
- Without `perf` the dTLB effect can't be isolated here. Worth re-measuring on a quiet box with `perf stat -e
  dTLB-load-misses` before asking for a shim change.
- If it does help there: the shim needs no new code path for the glibc route (the env var works on glibc ≥ 2.35), or
  the reader could `madvise(MADV_HUGEPAGE)` the index buffer (Main/Shim, Rowan's files; Lean has no madvise binding, so
  it would need the env var or a C shim).
