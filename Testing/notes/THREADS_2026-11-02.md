# Thread overhead on hg38: cause and fix (speed/n31-threads, 2026-11-02)

Box: 4 vCPU Xeon 2.1 GHz, 15 GB, release `bench-release` (shim.idx 5.3 GB, minibwa c07de5c index).
Shim: `lean-align map shim.idx R1 R2 out.sam 100 1000`, `taskset -c 0-(t-1)`. minibwa: `map -t t`.
Median of 3, one run at a time, each tool warmed once and run tool-major (its index stays cached).
multiple = minibwa ÷ ours (> 1: we are faster). Base shim SAM is all unmapped by design
(`Bridge.answerOf` sets `found := none`), so this is the router against minibwa's full alignment.

## Cause
- Same pairs (hg38 low 200k): 1 process on 1 core 21–23 s user; 2 separate 1-core processes on the halves
  10.4 + 10.6 s; 1 process on 2 cores 26–28 s; on 4 cores 37–45 s. System time flat (~5 s, the index read).
  So the extra CPU is inside one process, in user space. minibwa's CPU is flat from 2 to 4 threads here.
- `valgrind --tool=callgrind --collect-bus=yes` (counts locked instructions), 2k pairs: 1.65M locked ops
  (~826/pair). The contended ones: `ix.sl` is the loaded `index` ByteArray itself, captured by every
  alignPairs task, hence thread-shared; `slotW`/`rdSlot`, inlined into `scanAWK`, made the compiler pass it
  through join points as owned: an atomic inc + dec on one cache line per scanned bucket slot, from all cores.

## Fix (SAM byte-identical on all 5 sets × 2/4 threads × 3 runs)
1. `slotW`, `rdSlot`: `@[noinline]` and `(B : @& ByteArray)` (attributes only; definitions and theorems
   unchanged). Locked ops 1.65M → 0.75M; low 200k 4 cores user 37–40 s → 23–25 s.
2. `ParMap.parMapS` (proved `= xs.map (f (mk ()))`): each task runs `loadIndex`/`chunkSetup` itself, so its
   records and closures keep single-threaded counts. 23.3–24.8 s → 21.3–22.5 s (= the 1-core cost).
Remaining locked ops are on per-pair objects (task results freed, read bytes): uncontended.
